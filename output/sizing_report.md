## 7. Latency budget

Two different measurements. **L1** (what the pipeline controls) starts at collector receipt (`received_at`). **L2** (what a customer sees) starts at SDK event creation and adds SDK buffering, network, and retries, which we cannot change or observe server-side. Summing poll wait and batching window is conservative: they can overlap. All values are estimates, none measured.

### L1: collector receipt -> visible on dashboard

| stage | typical | worst (no retry) | label / basis |
|---|---|---|---|
| collector validate + PutRecords + response | 30 ms | 50 ms | [Estimated] |
| Kinesis availability + Lambda poll | 500 ms | 1000 ms | [Benchmarked] ESM polls each shard once per second; polling consumers see 'typically below 1 second' propagation |
| batching window (BatchSize 500 needs >= 1 s) | 1000 ms | 1000 ms | [Benchmarked] API rule; at normal traffic (~24 ev/s/shard) a 500-record batch never fills, so the full window is spent [Estimated] |
| Lambda batch + Valkey Lua pipeline | 150 ms | 300 ms | [Estimated]; must benchmark |
| dashboard read (Valkey) + client refresh | 500 ms | 1000 ms | 1 s poll or push [Assumed] |
| **total** | **2.18 s** | **3.35 s** | [Estimated]; 1.65 s headroom vs 5 s in the worst non-retry case |
| tail: Lambda retry / bisect |  | +1-3 s per retry | [Estimated] |
| tail: backlog (IteratorAge) |  | unbounded | alarm at 30 s, page at 5 min |

### L2: SDK event creation -> collector receipt (added on top of L1)

| stage | estimate | label |
|---|---|---|
| SDK buffering / flush interval | unknown | SDK discovery item |
| browser -> ALB network + TLS | 50-300 ms | [Assumed] |

L1 worst case leaves 1.65 s of the 5 s target for L2. Whether the 5 s target holds end-to-end depends on the SDK's flush interval, which must be measured. Plan: synthetic canary events every 10 s through the real endpoint (L1, server clock), plus a headless browser running the real SDK with a synchronized clock (L2).

## 11. Cost uncertainties

- **RDS backup storage**: free up to the account's total provisioned database storage in the region [Benchmarked: https://aws.amazon.com/rds/faqs/]; beyond that $0.095/GB-month. With 7-day retention and modest churn the line is $0; if backups grew to an extra 1x of DB size: $19/month.
- **Athena MERGE INTO and VACUUM billing** is not stated in AWS docs (DELETE and OPTIMIZE are documented as billed by data scanned); the model assumes MERGE is billed by data scanned too.
- **Cross-AZ charges for ElastiCache replication, RDS Multi-AZ replication, and ALB-to-target traffic** were not verified and are not included.
- **Firehose 5 KB rounding** on the raw stream is the conservative reading of the pricing page; a `KDS-no-rounding` SKU at $0.074/GB exists in the price list but its applicability is undocumented.
- **Firehose Iceberg destination** SKUs ($0.045 and $0.075/GB) have unclear applicability; the design avoids them (packed staging + hourly Athena MERGE).
- **WAF request tier** applicability is unclear; WAF is shown as optional.
- All usage quantities marked [Assumed] (log volume, metric count, Athena scans, S3 requests) dominate small lines; none dominates the total.
